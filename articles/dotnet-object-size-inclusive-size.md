# C#/.NET のオブジェクトサイズを読む — 80B と包括サイズ 112B の違い

メモリプロファイラーで、ある C# のクラスに「サイズ 80B」「包括サイズ 112B」と表示されたとする。この差は、**インスタンス本体のサイズ**と、**参照先のオブジェクトを含めたサイズ**を区別すると説明できる。

本記事では、`int` が 7 個、`float` が 5 個、`int` を基底型とする `enum` が 1 個、`string` フィールドが 1 個あるクラスを例に、サイズの内訳を考える。B はバイトを表す。

## 計算の前提

以下は、**64 ビットプロセスで動く .NET の CoreCLR**を想定した計算例である。

- オブジェクトへの参照は 8B。
- `int` と `float` はそれぞれ 4B、今回の `enum : int` も 4B。
- 通常のオブジェクトには、フィールド以外の共通領域が合計 16B ある。
- ヒープ上の確保領域は、ここでは 8B 単位に切り上げて考える。
- 基底クラスに追加のインスタンスフィールドはなく、明示的なレイアウト指定もない。

これらは C# 言語仕様がすべての実行環境に保証する配置ではない。32 ビットプロセスや別のランタイム、レイアウト指定がある型では、同じ数字になるとは限らない。以下の CoreCLR の実装説明は .NET 10.0.0 のソースを参照している。

## 対象のクラス

```csharp
enum MyEnum : int
{
    None = 0,
    Value = 1
}

sealed class Sample
{
    public int A, B, C, D, E, F, G;
    public float X1, X2, X3, X4, X5;
    public string? Name;
    public MyEnum Type;
}
```

`Name` は文字列本体を格納するフィールドではなく、`string` オブジェクトへの参照を格納するフィールドである。`string?` の `?` は null を許容する注釈であり、参照の格納サイズを増やすものではない。

## なぜインスタンス本体は 80B になるのか

まず、各フィールドとオブジェクトの共通領域を合計する。

| 内容 | 個数 | 1 個あたり | 合計 |
|---|---:|---:|---:|
| `int` | 7 | 4B | 28B |
| `float` | 5 | 4B | 20B |
| `enum : int` | 1 | 4B | 4B |
| `string` への参照 | 1 | 8B | 8B |
| オブジェクトの共通領域（ヘッダー等） | 1 | 16B | 16B |
| **切り上げ前の合計** | | | **76B** |

ここでいう 16B は、同期ブロック情報などを保持するヘッダー領域 8B と、型情報（MethodTable）へのポインター 8B を合わせたものを指す。CoreCLR のソース上では、それぞれ `OBJHEADER_SIZE` と `OBJECT_SIZE` として定義されている。型情報本体を各インスタンスに丸ごと格納するわけではない。[CoreCLR のオブジェクト定義](https://github.com/dotnet/runtime/blob/v10.0.0/src/coreclr/vm/object.h)

76B を 8B 単位に切り上げると、80B になる。

```text
フィールドの合計     60B
ヘッダー等           16B
アラインメントの余白  4B
------------------------
インスタンス本体     80B
```

アラインメントとは、メモリ上の配置を一定の境界にそろえることである。この例では、サイズ計算に合計 4B の余白（パディング）が必要になる。

なお、この内訳は実際のフィールドの配置順を示すものではない。通常の C# クラスではランタイムが配置を決めるため、宣言順にそのまま並ぶとは限らない。

したがって、この条件でプロファイラーが単一の `Sample` に 80B と表示するなら、型の構成から計算した値と整合している。

## `string` 本体は別のオブジェクトにある

`Sample` の中にあるのは、`Name` の参照を格納する 8B の領域である。文字列の長さや UTF-16 のデータは、その参照が指す別の `string` オブジェクトにある。

たとえば、次のように長さ 5 の文字列を設定する。

```csharp
var sample = new Sample
{
    Name = new string('A', 5),
    Type = MyEnum.Value
};
```

この場合の参照関係は次のようになる。

```mermaid
flowchart LR
    sample["Sample 本体: 80B<br/>Name の参照領域 8B を含む"]
    text["別の string オブジェクト: 32B<br/>長さ 5 の UTF-16 データ等"]
    sample -->|"Name が参照"| text
```

`Name` の参照領域 8B は、すでに `Sample` の 80B に含まれている。参照先のサイズを足すときに、この 8B をもう一度加算する必要はない。

### 32B の文字列を説明する計算例

今回のモデルでは、長さ `n` の `string` に必要な領域を次のように見積もる。

```text
8B 単位に切り上げる前のサイズ
  = ヘッダー等 16B + 長さの領域 4B + UTF-16 データ 2 × n B
    + ランタイム内部の終端用領域 2B
  = 22 + 2 × n B
```

長さ 5 なら `22 + 2 × 5 = 32B` となる。これは CoreCLR の `StringObject::GetBaseSize()` と `StringObject::GetSize()` に対応する計算である。[CoreCLR の文字列サイズ計算](https://github.com/dotnet/runtime/blob/v10.0.0/src/coreclr/vm/object.inl)

`n` は `string.Length`、つまり UTF-16 コード単位の数である。絵文字などでは、見た目の 1 文字が複数のコード単位になることがある。[`String.Length` の定義](https://learn.microsoft.com/en-us/dotnet/api/system.string.length?view=net-10.0)

サイズはアラインメントによって段階的に増えるので、長さが増えるたびに必ず表示サイズが増えるわけではない。また、32B という数字だけから文字列の長さを一意に決めることはできない。

## 「包括サイズ 112B」は何を含むのか

Performance Explorer などで表示される「包括」が **Inclusive Size** を意味する場合、インスタンス本体に加え、参照先のオブジェクトも含めたサイズを表す。Visual Studio のメモリ使用量レポートでも、Inclusive Size は参照先を含むサイズとして説明されている。[Visual Studio のメモリ使用量レポート](https://learn.microsoft.com/en-us/visualstudio/profiling/memory-usage?view=vs-2022#managed-types-reports)

単一の `Sample` が、計算対象となる 32B の `string` を 1 個参照しているなら、次の内訳が成立する。

| 対象 | サイズ |
|---|---:|
| `Sample` 本体 | 80B |
| `Name` が参照する `string` 本体 | 32B |
| **包括サイズ** | **112B** |

```text
80B + 32B = 112B
```

したがって、「本体 80B、包括 112B」という表示は、32B の文字列が参照先にあるという説明とよく一致する。

ただし、元の画面や参照関係を確認しない限り、差分の 32B が必ず文字列 1 個によるものだとは断定できない。プロファイラーがサイズに含めるアラインメントの扱いや、共有された参照先の集計方法も確認する必要がある。

## 文字列が長くなった場合と、共有されている場合

`Name` をより長い文字列への参照に置き換えても、`Sample` 本体にある参照領域は 8B のままである。そのため、同じ型のインスタンス本体は基本的に 80B のままで、参照先を含むサイズが変わる。`string` は不変なので、文字列オブジェクトそのものを伸ばすのではなく、別の文字列への参照を設定することになる。

`Name` が null でも、参照を格納する 8B の領域は存在する。一方、null の参照先には `string` オブジェクトがないため、その分を包括サイズに加算することはない。

同じ `string` を複数の `Sample` が参照することもある。文字列リテラルのインターンなどによる共有があると、包括サイズを各行から単純に足しても、ヒープ全体のサイズにはならない。包括サイズは、そのオブジェクトが回収された場合に、あわせて回収可能になるメモリ量（Retained Size）と同じとは限らない。

## プロファイラーで確認するポイント

1. 対象アプリケーションが 64 ビットプロセスか確認する。開発マシンが 64 ビットであることだけでは判断できない。
2. 「サイズ」「包括サイズ」の列の定義を確認する。CPU プロファイルなど、別のレポートにある「包括」は意味が異なる。
3. 型ごとの集計行なのか、単一インスタンスの行なのかを確認する。型の行では個数も確認し、複数インスタンスの合計を 1 個のサイズとして読まない。
4. 対象インスタンスの参照先を開き、`Name` が指す `string` のサイズと共有状況を確認する。
5. 文字列の長さを変え、本体のサイズと包括サイズの変化を比較する。

フィールドの合計だけでなく、ヘッダー等、参照のサイズ、アラインメントまで考えると、本体 80B の理由が分かる。さらに参照先を確認すれば、包括 112B との差分を説明できる。**型からの計算と、プロファイラーが示す実際のオブジェクト構成を照合することが、サイズ表示を理解するためのよい確認になる。**
